# Data Model: GitHub Deck Distribution

This feature adds no application database or vocabulary schema. It defines relationships among repository revisions, workflow outputs, release versions, and existing Anki identities.

## Repository Revision

- **Attributes**: Commit SHA, source files, vocabulary TSV, referenced media, templates, project code, dependency configuration.
- **Identity**: Commit SHA, with a release tag resolving to that revision for a particular run.
- **Validation**: Existing project validation and quality commands must pass on the checked-out revision before an artifact is treated as successful.

## Release Tag

- **Attributes**: Git ref name and target repository revision.
- **Valid release form**: `vMAJOR.MINOR.PATCH`, where each component is decimal digits. The workflow event filter `v*.*.*` is followed by exact validation of this form.
- **Relationship**: One release tag maps to one GitHub Release. A tag is an explicit distribution trigger; a normal main push has no release transition.
- **Identity independence**: Tag text is never an input to concept IDs, note GUIDs, deck ID, or note-model ID.

## Deck Package

- **Attributes**: Standard Anki package bytes generated by the existing build command, source revision, local path `dist/myid-anki.apkg`.
- **Identity and content**: The existing generator controls deck/model IDs and note GUIDs. Copying or renaming the archive for distribution does not modify its contents.
- **Relationships**: A successful CI run can expose it as a run artifact. A successful tagged run can expose it as one Release asset named `indonesian-malaysian.apkg`.

## CI Artifact

- **Attributes**: Clear artifact name, source workflow run, packaged `myid-anki.apkg`, repository-configured retention period.
- **Role**: Maintainer inspection and same-run transfer between release jobs; not the learner-facing download.
- **Validation**: Missing package or failed attempted upload fails the producing job. Release publication downloads only the named artifact from its own workflow run.

## GitHub Release and Asset

- **Attributes**: Version tag, release page, one deck asset named `indonesian-malaysian.apkg`.
- **Relationship**: The release asset is a renamed copy of the checked package from the same tagged run.
- **Transition**: Absent → draft after all gates pass → published only after checked asset upload. Existing published release → draft before asset replacement → published with one stable-named asset after successful upload. Failed checks leave any existing deck asset untouched; failed publication leaves a draft pending retry rather than an assetless completed release.

## Permanent Concept ID and Anki Identity

- **Attributes**: Existing six-digit concept ID, derived note GUID, stable deck ID, stable note-model ID.
- **Relationship**: One concept produces one note and card. Release tags and asset filenames have no relationship to identity derivation.
- **Transition**: Mutable vocabulary or media edits with the same concept ID preserve its GUID. Omission from a later package does not request deletion from an existing collection; reintroduction with the same ID restores the same GUID.

## Workflow State Transitions

1. Pull request or main push → checkout revision → environment/dependencies → validate → test → lint → format check → build → artifact upload → successful CI result. Any failed required step, including attempted upload, ends in failure.
2. Matching tag push → checkout tagged revision → exact tag guard → same five quality/build steps → same-run artifact upload → read-only build job succeeds.
3. Successful release build → write-scoped publication job downloads its own run artifact → renames a copy → creates or updates tag's Release asset. Publication failure yields a failed workflow and must not claim a successful deck asset.
